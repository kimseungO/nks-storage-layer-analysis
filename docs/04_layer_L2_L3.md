# 04. L2 / L3 — Ceph 분산 스토리지와 파일시스템 계층

## 목적

전체 성능 손실의 대부분이 발생하는 구간을 분석합니다.

- **L2**: 동일한 VM에서 대상만 물리 파티션 → Ceph RBD로 변경하여 분산 스토리지 계층의 비용을 분리합니다.
- **L3**: 동일한 RBD 볼륨에 ext4를 얹어 파일시스템 계층의 비용을 분리합니다.

---

## 1. 실험 구성

### 측정 대상

```
L1 : ubuntu01 → /dev/vdd        (물리 파티션 직결)
L2 : ubuntu01 → /dev/rbd0       (Ceph RBD, raw)
L3 : ubuntu01 → /mnt/rbd-l3/testfile  (동일 RBD + ext4)
```

**세 계층 모두 동일한 VM(ubuntu01)에서 측정했습니다.** CPU, 커널, 메모리 조건이 완전히 같으므로 변인이 통제됩니다.

### RBD 매핑

```bash
# controller
rbd create volumes/bench-l2 --size 61440

# ubuntu01
rbd map volumes/bench-l2      # → /dev/rbd0
```

커널 RBD 모듈을 사용하여 블록 디바이스로 직접 매핑했습니다. QEMU/librbd 경로를 거치지 않으므로 Ceph 자체의 비용만 측정됩니다.

### 사전 조치

| 항목 | 조치 |
|------|------|
| 프리컨디셔닝 | L2: 20GB 순차 쓰기 / L3: 8GB 파일 생성 |
| 워킹셋 | `offset_increment=2G` (4잡 × 2GB) |
| 관측 | `ceph osd perf`, `ceph -s`, 호스트 `iostat -x 1` (OSD 파티션 3개) |

> 프리컨디셔닝 범위를 60GB 전체가 아닌 20GB로 제한한 이유는 Replica 3 환경에서 60GB 기록 시 180GB가 소모되어 클러스터 용량을 압박하기 때문입니다.

## 2. 측정 결과

### L2 — Ceph RBD (raw)

| 종목 | IOPS | Bandwidth | 평균 lat |
|------|:----:|:---------:|:--------:|
| randwrite 4K | **8,974** | 35.1 MiB/s | 14.26 ms |
| randread 4K | **24,300** | 95.1 MiB/s | 5.26 ms |
| seqwrite 1M | 348 | **349 MiB/s** | 45.84 ms |
| seqread 1M | 2,172 | **2,172 MiB/s** | 7.36 ms |

### L3 — Ceph RBD + ext4

| 종목 | IOPS | Bandwidth | 평균 lat |
|------|:----:|:---------:|:--------:|
| randwrite 4K | **8,913** | 34.8 MiB/s | 14.36 ms |
| randread 4K | **26,000** | 101 MiB/s | 4.92 ms |
| seqwrite 1M | 407 | **407 MiB/s** | 39.28 ms |
| seqread 1M | 2,094 | **2,094 MiB/s** | 7.64 ms |

### 계층 간 비교

| 종목 | L1 (KVM raw) | L2 (Ceph) | L1→L2 잔존율 | L3 (ext4) | L2→L3 변화 |
|------|:------------:|:---------:|:------------:|:---------:|:----------:|
| randwrite 4K | 255,000 | 8,974 | **3.5%** | 8,913 | -0.7% |
| randread 4K | 310,000 | 24,300 | **7.8%** | 26,000 | +7.0% |
| seqwrite 1M | 5,214 | 349 | **6.7%** | 407 | +16.6% |
| seqread 1M | 6,592 | 2,172 | **32.9%** | 2,094 | -3.6% |

**L1 → L2에서 96.5%가 소실됩니다. 이 프로젝트에서 발견한 최대 병목입니다.**

## 3. L2 분석 — Ceph가 부과하는 비용

### 3-1. I/O 경로의 변화

```
L1 (물리 직결)
  게스트 → virtio → 물리 디스크
           약 2 µs

L2 (Ceph 경유)
  게스트 → librbd/krbd
        → 오브젝트 매핑 계산 (CRUSH)
        → 네트워크 전송 → Primary OSD
        → Primary가 복제본 2개에 전파, 양쪽 응답 대기
        → 각 OSD에서 BlueStore 처리
             ├ WAL(Write-Ahead Log) 기록
             ├ RocksDB 메타데이터 갱신
             └ 데이터 블록 기록
        → 응답
           약 107 µs
```

요청당 처리 시간으로 환산하면 다음과 같습니다.

```
L1 요청당 시간 : 1초 ÷ 255,000 =   3.9 µs
L2 요청당 시간 : 1초 ÷   8,974 = 111.4 µs
→ Ceph 추가 비용 ≈ 107 µs
```

virtio가 부과한 2µs와 비교하면 **약 50배 규모**입니다.

### 3-2. 쓰기 증폭 — 1:1 대응이 깨집니다

L0/L1에서 fio 보고량과 물리 디스크 기록량이 일치했으나, L2부터 어긋납니다.

| 종목 | fio 클라이언트 | 물리 3개 합계 | 비율 |
|------|:-------------:|:------------:|:----:|
| randwrite 4K | 36.8 MB/s | ~290 MB/s | **7.9x** |
| seqwrite 1M | 366 MB/s | ~990 MB/s | **2.7x** |
| randread 4K | 99.7 MB/s | ~105 MB/s | 1.05x |
| seqread 1M | 2,278 MB/s | ~2,250 MB/s | 0.99x |

**쓰기만 증폭되고 읽기는 그대로입니다.** 복제가 쓰기 경로에만 존재하기 때문입니다.

randwrite의 7.9배는 두 요인의 곱입니다.

```
Replica 3 (3배) × BlueStore 내부 다중 쓰기 (약 2.6배) ≈ 7.9배
```

BlueStore는 작은 쓰기를 처리할 때 WAL에 먼저 기록한 후 데이터 블록에 반영합니다. 이 이중 쓰기가 OSD 3개에서 각각 발생합니다.

seqwrite의 증폭률이 2.7배로 낮은 이유는, **BlueStore가 크고 정렬된 쓰기는 WAL을 우회하여 직접 기록**하기 때문입니다. 대형 순차 쓰기에서는 이중 쓰기 페널티가 사라집니다.

### 3-3. 요청 크기 변화

| 계층 | randwrite `wareq-sz` |
|------|:--------------------:|
| L0 / L1 | 4.00 KB |
| L2 | **8.7 KB** |

클라이언트가 4KB로 요청했으나 물리 디스크에는 8.7KB 단위로 기록됩니다. BlueStore가 WAL 기록과 데이터 기록을 병합하면서 요청 크기가 증가한 결과입니다.

### 3-4. seqread만 33%를 유지한 이유

4종 중 유일하게 선방했습니다. **불리한 조건이 하나도 없기 때문입니다.**

| 종목 | 요청 횟수 부담 | 복제 부담 | 잔존율 |
|------|:-------------:|:---------:|:------:|
| randwrite 4K | 큼 | 큼 | 3.5% |
| randread 4K | 큼 | 없음 | 7.8% |
| seqwrite 1M | 작음 | 큼 | 6.7% |
| **seqread 1M** | **작음** | **없음** | **32.9%** |

순차이므로 요청당 고정 비용이 희석되고, 읽기이므로 복제 전파가 없습니다.

### 3-5. OSD 읽기 부하 불균형

randread 구간의 `iostat` 출력에서 파티션별 읽기량 차이가 관측되었습니다.

```
nvme*p3 (osd.2) :  ~8,400 r/s
nvme*p4 (osd.3) :  ~7,000 r/s
nvme*p5 (osd.1) : ~11,000 r/s   ← 약 40% 높음
```

Ceph 읽기는 **PG의 Primary OSD만 처리**합니다. PG 32개를 OSD 3개에 배분하면 균등 분배가 성립하지 않으며, osd.1이 Primary인 PG가 더 많이 할당된 결과입니다.

쓰기에서는 모든 OSD가 복제본을 받으므로 이 불균형이 드러나지 않습니다. **읽기 워크로드에서만 관측되는 특성**이며, PG 수를 늘리면 완화됩니다.

### 3-6. OSD 지연 관측

`ceph osd perf`의 `apply_latency`는 유휴 시 0~2ms를 유지하다가, seqwrite 구간에서 **최대 27ms**까지 상승했습니다.

읽기 테스트에서는 유의미한 변화가 없었습니다. `apply_latency`는 쓰기를 디스크에 적용하는 시간을 측정하므로, 읽기 부하에서는 측정 대상이 발생하지 않습니다.

> **읽기 병목 진단 시 `ceph osd perf`는 적절한 도구가 아니라는 점**이 부수적으로 확인되었습니다.

## 4. L3 분석 — 파일시스템 계층

### 4-1. 오버헤드가 관측되지 않았습니다

| 종목 | L2 | L3 | 변화 |
|------|:--:|:--:|:----:|
| randwrite 4K | 8,974 | 8,913 | -0.7% |
| randread 4K | 24,300 | 26,000 | +7.0% |
| seqwrite 1M | 349 | 407 | **+16.6%** |
| seqread 1M | 2,172 | 2,094 | -3.6% |

ext4 계층의 비용은 측정 오차 수준이며, seqwrite는 오히려 향상되었습니다.

### 4-2. seqwrite가 향상된 이유

파일시스템이 개입하면 커널 블록 레이어가 요청을 병합할 기회를 얻습니다. `iostat`에 흔적이 남습니다.

```
L2 seqwrite : w/s ~6,000, wareq-sz 105 KB
L3 seqwrite : w/s ~5,500, wareq-sz 113 KB
```

요청 수는 감소하고 요청당 크기는 증가했습니다. Ceph 입장에서 처리할 요청 건수가 줄어들므로 유리하게 작용합니다.

## 5. Little's Law 검증

| 계층 | 종목 | 예측값 | 실측값 | 오차 |
|------|------|:------:|:------:|:----:|
| L2 | randwrite | 128 ÷ 8,974 = 14.26 ms | 14.259 ms | 0.01% |
| L2 | randread | 128 ÷ 24,300 = 5.27 ms | 5.256 ms | 0.3% |
| L2 | seqwrite | 16 ÷ 348 = 45.98 ms | 45.84 ms | 0.3% |
| L2 | seqread | 16 ÷ 2,172 = 7.37 ms | 7.361 ms | 0.1% |
| L3 | randwrite | 128 ÷ 8,913 = 14.36 ms | 14.357 ms | 0.02% |
| L3 | randread | 128 ÷ 26,000 = 4.92 ms | 4.919 ms | 0.02% |
| L3 | seqwrite | 16 ÷ 407 = 39.31 ms | 39.28 ms | 0.08% |
| L3 | seqread | 16 ÷ 2,094 = 7.64 ms | 7.637 ms | 0.04% |

Ceph를 경유하는 환경에서도 수식이 그대로 성립합니다.

---

## 6. 결론

| 항목 | 결과 |
|------|------|
| Ceph 계층 비용 (randwrite) | **96.5% 손실** — 요청당 약 107 µs 추가 |
| Ceph 계층 비용 (seqread) | 67% 손실 — 4종 중 최소 |
| 쓰기 증폭 | randwrite 7.9x / seqwrite 2.7x |
| 읽기 증폭 | 없음 (1:1 유지) |
| ext4 계층 비용 | **측정 오차 수준 (1% 이내)** |

> **분산 스토리지 계층이 전체 성능 손실의 대부분을 차지합니다.**
> 복제본 전파, 네트워크 왕복, BlueStore의 WAL 기반 다중 쓰기가 요청당 약 107µs를 추가하며, 이는 물리 디스크 처리 시간(1.82µs)의 약 59배입니다. 반면 파일시스템 계층은 덮어쓰기 워크로드에서 오버헤드가 관측되지 않았습니다.

이 시점부터 병목이 Ceph로 고정되므로, 이후 계층에서 추가되는 비용은 상대적으로 흡수됩니다. L3 → L4 구간에서 이 현상이 확인됩니다.
