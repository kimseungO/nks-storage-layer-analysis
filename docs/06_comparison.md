# 06. NKS 대조 분석 및 QoS 검토

## 목적

L5(재현 스택의 K8s Pod)와 L6(NKS Pod)는 동일한 형태의 측정 지점입니다. 두 값을 대조하여, [01_problem.md](01_problem.md)에서 제기한 세 가지 가설 중 어느 것이 NKS의 측정 결과를 가장 잘 설명하는지 검토합니다.

---

## 1. 검토 대상 가설

01번 문서에서 세 가지 가설이 동일한 측정 결과를 만들 수 있음을 확인했습니다.

| 가설 | 설명 |
|------|------|
| A. 하드웨어 한계 | 백엔드 디스크가 실제로 느림 |
| B. 네트워크 지연 | 스토리지 노드까지의 왕복 지연 |
| C. QoS 정책 | 볼륨당 IOPS 상한 설정 |

managed 환경에서는 백엔드를 직접 관측할 수 없으므로, **동등한 형태의 스택에서 얻은 측정값을 대조군으로 삼아 간접적으로 검토**합니다.

---

## 2. L5 ↔ L6 대조

### 측정 조건 비교

| 항목 | L5 (재현 스택) | L6 (NKS) |
|------|---------------|----------|
| 측정 위치 | K8s Pod 내부 | K8s Pod 내부 |
| 볼륨 | PVC + ext4 | PVC + ext4 |
| StorageClass | `cinder-rbd` | `cinder-default` |
| 프로비저너 | Cinder | Cinder |
| 측정 도구 | `ljishen/fio` | `ljishen/fio` |
| fio 조건 | 4종 동일 | 4종 동일 |

두 환경 모두 Cinder를 프로비저너로 사용하는 K8s Pod입니다. 다만 **NKS의 백엔드 스토리지가 무엇인지는 확인할 수 없으므로, 두 환경이 완전히 동일한 구성이라고 단정할 수는 없습니다.** 비교 가능한 것은 "Pod에서 PVC에 접근했을 때 나타나는 성능"이라는 관점에서의 대조입니다.

### 결과 비교

| 종목 | L5 (재현) | L6 (NKS) | 비율 |
|------|:---------:|:--------:|:----:|
| randwrite 4K | 8,447 IOPS | **2,002 IOPS** | 23.7% |
| randread 4K | 21,300 IOPS | **2,007 IOPS** | 9.4% |
| seqwrite 1M | 400 MiB/s | **53.2 MiB/s** | 13.3% |
| seqread 1M | 1,391 MiB/s | **64.1 MiB/s** | 4.6% |

| 지연 지표 | L5 | L6 |
|-----------|:--:|:--:|
| randwrite 평균 lat | 15.15 ms | **63.90 ms** |
| randwrite p99 | 181 ms | 78 ms |
| randwrite p99.99 | 1,468 ms | **128 ms** |

## 3. QoS 제한을 시사하는 관측

### 관측 1 — 읽기와 쓰기가 동일합니다

전 계층에서 확인된 읽기·쓰기 비율입니다.

| 계층 | randwrite | randread | 읽기/쓰기 비율 |
|------|:---------:|:--------:|:-------------:|
| L0 물리 | 550,000 | 559,000 | 1.02 |
| L1 KVM | 255,000 | 310,000 | 1.22 |
| L2 Ceph | 8,974 | 24,300 | **2.71** |
| L3 ext4 | 8,913 | 26,000 | **2.92** |
| L4 인스턴스 | 8,548 | 20,700 | **2.42** |
| L5 K8s | 8,447 | 21,300 | **2.52** |
| **L6 NKS** | **2,002** | **2,007** | **1.00** |

Ceph를 경유하는 계층(L2~L5)에서는 읽기가 쓰기보다 2.4~2.9배 빠르게 측정되었습니다. 쓰기는 복제본 전파와 BlueStore 다중 쓰기를 거치는 반면, 읽기는 Primary OSD가 응답하는 구조에서 비롯된 것으로 보입니다.

**NKS만 비율이 1.00입니다.** 복제를 수행하는 분산 스토리지라면 쓰기가 더 무거울 것으로 예상되므로, 이 결과는 백엔드 스토리지의 물리적 특성이 측정값에 반영되지 않았을 가능성을 시사합니다.

> 이 논리는 NKS 백엔드가 복제 기반 분산 스토리지라는 전제에 의존합니다. 다만 퍼블릭 클라우드의 블록 스토리지가 어떤 형태로든 이중화를 수행한다는 점을 고려하면, 읽기와 쓰기가 완전히 동일한 성능을 보이는 것은 부자연스러워 보입니다.

### 관측 2 — 변동성이 매우 낮습니다

60초 측정 구간의 순간 IOPS 분포입니다.

```
L5 randwrite : min     36 ~ max 4,517   (clat 표준편차 52,126 µs)
L6 randwrite : min    458 ~ max   634   (clat 표준편차  6,315 µs)
```

L5는 SSD 가비지 컬렉션, Ceph OSD 큐 상태, PG 분포 등의 영향으로 순간 성능이 크게 변동합니다. 반면 L6는 좁은 범위에서 평탄하게 유지됩니다.

이러한 패턴은 **속도를 일정하게 제어하는 장치가 개입하고 있는 것을 보입니다.**

### 관측 3 — Little's Law에 정확히 부합합니다

`Latency = Queue Depth / Throughput`

```
Queue Depth = iodepth 32 × numjobs 4 = 128

L6 randwrite : 128 ÷ 2,002 IOPS = 63.93 ms
실측 평균 latency                = 63.90 ms
→ 오차 0.05%
```

seq 테스트에서도 유사합니다.

```
L6 seqwrite : 16 ÷ 53 = 301.9 ms   (실측 299.89 ms)
L6 seqread  : 16 ÷ 64 = 250.0 ms   (실측 249.41 ms)
```

계산값과 실측값이 거의 일치한다는 것은, **63.9ms의 대부분이 디스크 처리 시간이 아니라 큐 대기 시간일 가능성**을 시사합니다.

만약 백엔드 디스크 자체가 상당한 처리 지연을 갖는다면 다음과 같이 나타났을 것으로 예상됩니다.

```
실제 지연 = 큐 대기 시간 + 디스크 처리 시간
         = 63.93 ms  + α
         → 실측값이 계산값보다 유의하게 커야 함
```

α가 0에 수렴하는 것으로 보이는 결과는 처리 시간이 무시할 수준이며, 지연의 대부분이 대기에서 발생했음을 뒷받침합니다.

## 4. 가설 검토 결과

| 가설 | 평가 | 근거 |
|------|:----:|------|
| A. 하드웨어 한계 | 가능성 낮음 | 동등한 형태의 스택(L5)이 4~20배 높은 성능을 보임. 읽기·쓰기가 동일한 현상은 하드웨어 특성으로 설명하기 어려움 |
| B. 네트워크 지연 | 가능성 낮음 | 네트워크 왕복 지연이 지배적이라면 Little's Law 계산값을 초과하는 latency가 관측되어야 하나, 오차 0.05%로 일치함 |
| C. QoS 정책 | **가장 개연성 높음** | 4종 모두 좁은 범위에 고정, 변동성 부재, Little's Law 완전 일치 |

> **NKS에서 측정된 2,002 IOPS는 백엔드 스토리지의 성능 한계라기보다, 볼륨에 적용된 IOPS 상한 정책의 결과로 보입니다.**
>
> 다만 이는 외부 관측 지표에서 도출한 추론이며, 실제 정책 설정값을 확인한 것은 아닙니다. 확정을 위해서는 볼륨 크기나 타입을 변경한 대조 실험, 또는 공식 문서상의 성능 규격 확인이 필요합니다.

## 5. 성능과 예측 가능성의 관계

처리량만 보면 재현 스택이 우월하나, 다른 지표를 함께 보면 해석이 달라집니다.

| 지표 | L5 (self-managed) | L6 (NKS) | 우위 |
|------|:-----------------:|:--------:|:----:|
| randwrite IOPS | 8,447 | 2,002 | L5 |
| 평균 latency | 15.15 ms | 63.90 ms | L5 |
| **p99.99 latency** | **1,468 ms** | **128 ms** | **L6** |
| **IOPS 변동폭** | **36 ~ 4,517** | **458 ~ 634** | **L6** |

**L5는 최악의 경우 1.47초를 대기하며, 순간 IOPS가 36까지 떨어지는 구간이 존재합니다.** 반면 L6는 60초 내내 일정한 수준을 유지합니다.

이는 우열이라기보다 설계 목표의 차이로 보는 것이 타당할 것으로 생각됩니다.

```
Self-managed : 하드웨어 성능을 온전히 사용, 대신 tail latency 예측이 어려움
Managed      : 처리량 상한을 두어 지연 편차를 억제
```

퍼블릭 클라우드는 다수 테넌트가 물리 자원을 공유하므로, 특정 테넌트의 폭발적 I/O가 다른 테넌트에 영향을 주지 않도록 격리할 필요가 있습니다. **이러한 맥락에서 QoS 상한은 성능을 제한하는 제약이라기보다, 예측 가능성을 확보하기 위한 설계 선택으로 이해하는 것이 적절해 보입니다.**

### 계층별 손실 기여도 (randwrite 4K)

| 구간 | 추가 계층 | 손실률 | 추정 원인 |
|------|-----------|:------:|-----------|
| L0 → L1 | KVM 가상화 | 53.6% | 요청당 고정비용 (약 2 µs) |
| L1 → L2 | **Ceph + Replica 3** | **96.5%** | **복제 + 네트워크 + BlueStore (약 107 µs)** |
| L2 → L3 | ext4 | 0.7% | 측정 오차 수준 |
| L3 → L4 | 중첩 가상화 | 4.1% | 하위 병목에 흡수된 것으로 보임 |
| L4 → L5 | K8s CSI + 컨테이너 | 1.2% | 측정 오차 수준 |
| L5 → L6 | **managed 플랫폼** | **76.3%** | **정책적 상한으로 추정** |

```
물리 550,000 IOPS
  │
  ├─ KVM      ─ 절반 소실 (하드웨어가 빨라 virtio 비용 비중이 큼)
  │
  ├─ Ceph     ─ 96.5% 소실  ★ 최대 병목
  │
  ├─ ext4     ─ 영향 없음
  ├─ 중첩가상화 ─ 4%
  ├─ K8s      ─ 영향 없음
  │
  └─ NKS      ─ 2,000 IOPS 수준으로 고정
```

## 7. 결론

### 기술적 결론

**첫째, 본 환경에서 병목은 Ceph 계층에 집중되어 있습니다.** 물리 성능의 98.4%가 L1→L2 구간에서 소실되었으며, 파일시스템·중첩 가상화·K8s 계층을 모두 합쳐도 6% 미만이었습니다. 이러한 결과를 고려하면, 스토리지 성능 개선의 우선순위는 백엔드 튜닝(복제 정책, PG 수, BlueStore 설정)에 두는 것이 효율적일 것으로 생각됩니다.

**둘째, K8s 계층은 성능에 유의미한 영향을 주지 않는 것으로 관측되었습니다.** CSI는 컨트롤 플레인에서 동작하고, 컨테이너는 커널을 공유하는 격리 방식이라는 구조적 특성에서 비롯된 것으로 보입니다. "K8s 전환 후 느려졌다"는 문의를 받았을 때, K8s 계층보다 백엔드와 볼륨 정책을 먼저 확인하는 것이 효율적일 것으로 판단됩니다.

**셋째, NKS의 성능 수치는 QoS 정책의 결과일 가능성이 높습니다.** 백엔드 하드웨어의 성능 한계로 보기 어려운 특징들이 관측되었습니다. 만약 이 해석이 맞다면, 더 높은 IOPS가 필요한 경우 볼륨 타입 변경이나 용량 조정 등 정책 계층에서 접근하는 것이 적절하며, 백엔드 성능을 문제 삼는 접근은 해결로 이어지지 않을 것으로 보입니다.

### 방법론적 결론

**관측이 제한된 시스템도 동등한 형태의 스택을 재현하여 간접적으로 분석할 수 있습니다.** managed 플랫폼의 내부를 직접 확인할 수 없더라도, 유사한 프로비저닝 경로를 갖는 스택을 구축하고 계층별로 분리 측정하면 각 계층의 기여도를 추정할 수 있습니다.

**Little's Law는 지연의 성격을 판별하는 데 유용한 도구입니다.** 지연이 `Queue Depth ÷ Throughput`에 근접하게 부합한다면, 그 지연의 대부분은 처리 시간이 아니라 대기 시간일 가능성이 높습니다. 이 프레임은 self-managed와 managed 양쪽에 동일하게 적용 가능하며, 본 실험의 전 계층에서 오차 0.3% 이내로 성립했습니다.

## 8. 한계 및 후속 과제

본 프로젝트의 결론은 다음과 같은 제약 조건 하에서 도출되었습니다.

| 항목 | 내용 |
|------|------|
| 백엔드 미확인 | NKS의 스토리지 백엔드가 Ceph인지 여부는 확인할 수 없음. `cinder-default` StorageClass명으로 Cinder 사용만 추정 가능 |
| QoS 수치 미검증 | 2,000 IOPS 상한이 볼륨 크기·타입에 따라 달라지는지 미확인. 볼륨 크기를 변경한 대조 실험 필요 |
| 단일 스핀들 제약 | OSD 3개가 동일 물리 디스크의 파티션을 사용. 실제 분산 환경의 네트워크 지연 특성은 반영되지 않음 |
| 덮어쓰기 워크로드 한정 | ext4 저널링 비용은 파일 생성·확장 워크로드에서 재측정 필요 |
| 캐시 영향 | 2GB 워킹셋은 OSD 노드 메모리(12GB)에 수용 가능. 대용량 워킹셋에서는 다른 결과가 나올 수 있음 |
| 단일 측정 | 각 계층·종목당 1회 측정. 반복 측정을 통한 통계적 신뢰구간은 산출하지 않음 |

특히 **NKS 백엔드를 확인할 수 없다는 점**은 이 프로젝트의 근본적 제약이자, 동시에 프로젝트를 시작하게 된 이유이기도 합니다. 관측 가능성이 제한된 환경에서 어디까지 추론할 수 있는지를 탐색한 시도로 이해해 주시면 좋겠습니다.
